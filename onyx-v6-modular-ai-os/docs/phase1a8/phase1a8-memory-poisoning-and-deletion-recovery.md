# Phase 1A.8 Wave 3B: Memory Poisoning Protection and Deletion Recovery

Wave 3B defines contract-only, deterministic boundaries for memory poisoning detection, source trust evaluation, content classification, authority-claim rejection, memory quarantine, durable-memory write eligibility validation, tombstone tracking, deletion propagation, derived-artifact invalidation, and deleted-memory non-resurrection validation.

Wave 3B does not execute:
- live durable-memory storage
- live memory writes
- live deletion execution
- live cache invalidation or rebuild
- live index rebuild
- live embedding generation
- live summary regeneration
- live backup restoration
- live archive retrieval
- live source rehydration
- context assembly or source ranking
- model routing
- Council Mode contracts
- Saved Draft contracts
- Automation Center V2 contracts
- accessibility contracts
- full Phase 1A.8 simulation
- final Phase 1A.8 validator
- active scheduler
- parallel memory writes

## Untrusted Sources

The following source classes are treated as untrusted by default and require poisoning detection, trust evaluation, instruction-content classification, authority-claim rejection, and write-eligibility validation:

- Issues
- emails
- documents
- web pages
- connector content
- external API content
- generated output
- agent output
- summaries
- embeddings
- retrieved low-trust content
- imported archives
- restored backups

Untrusted does not mean unusable. Untrusted means the source requires:
- provenance verification
- permission validation
- instruction-content classification
- authority-claim rejection
- poisoning checks
- redaction
- write-eligibility validation
- review or quarantine when policy requires it

## Source Trust Evaluation Contract

The `SourceTrustEvaluationContract` contains:

- `trustEvaluationId` - unique identifier
- `sourceReference` - reference to the source
- `sourceType` - `MemorySourceType` (USER_AUTHORED, REPOSITORY, EXTERNAL_DOCUMENT, etc.)
- `sourceAttribution` - who or what authored the source
- `declaredTrustClassification` - claimed trust level
- `evaluatedTrustClassification` - assessed trust level
- `instructionContentClassification` - classification as instruction vs. content
- `authorityClaims` - detected authority claims
- `promptInjectionIndicators` - detected injection indicators
- `provenanceVerified` - whether provenance is verified
- `permissionVerified` - whether permission is verified
- `freshnessVerified` - whether freshness is verified
- `redactionRequired` - whether redaction is needed
- `quarantineRequired` - whether quarantine is required
- `reviewRequired` - whether human review is required
- `durableWriteEligible` - whether eligible for durable memory write
- `evaluatorId` - who performed the evaluation
- `evaluatedAt` - when evaluation occurred
- `contractVersion` - "1.0.0"
- `evidenceReferences` - audit trail

**Critical invariant:** Trust classification does not automatically grant authority. A trusted source still requires scope, freshness, permission, and provenance validation.

## Instruction-Versus-Content Classification

The `InstructionContentClassificationContract` determines whether content should be treated as instruction or as content:

Classification types:
- `TRUSTED_USER_INSTRUCTION` - current user's explicit instructions
- `GOVERNANCE_INSTRUCTION` - active governance rules
- `REPOSITORY_INSTRUCTION` - repository documentation
- `SOURCE_CONTENT` - content from a source, not instruction
- `QUOTED_INSTRUCTION` - instruction found within other content
- `EMBEDDED_INSTRUCTION` - instruction embedded in untrusted content
- `UNTRUSTED_EXTERNAL_INSTRUCTION` - instruction from untrusted external source
- `MODEL_GENERATED_INSTRUCTION` - instruction generated by model
- `UNKNOWN_INSTRUCTION_CLASS` - unable to classify

**Critical rule:** Only validated current user instructions and active governance instructions may influence governed decisions within their permitted scope. Instructions found inside issues, emails, documents, web pages, connector content, generated output, agent output, summaries, or embeddings must be classified as content or untrusted embedded instruction.

**Embedded instruction must not override:**
- Rahul approval
- governance rules
- permission policy
- memory policy
- persona policy
- connector policy
- budget policy
- promotion policy
- security policy

## Prompt-Injection Indicator Contract

The `PromptInjectionIndicatorContract` detects and documents prompt-injection attempts:

Supported indicators:
- `ATTEMPT_OVERRIDE_PRIOR_INSTRUCTIONS` - explicit request to ignore prior instructions
- `CLAIM_HIDDEN_APPROVAL` - claim of approval not visible in governance
- `CLAIM_ADMINISTRATOR_AUTHORITY` - claim of administrator access
- `REQUEST_EXPOSE_SECRETS` - request to reveal secrets
- `REQUEST_BYPASS_PERMISSIONS` - request to skip permission checks
- `REQUEST_IGNORE_POLICY` - request to bypass policy
- `REQUEST_MODIFY_PERSONA` - request to change P0 baseline
- `REQUEST_EXECUTE_EXTERNAL_ACTIONS` - request to take external action
- `REQUEST_EXPAND_AGENT_AUTHORITY` - request to grant new authority
- `REQUEST_DURABLE_MEMORY_WRITE_UNGOERNED` - request to write memory without governance
- `REQUEST_SUPPRESS_EVIDENCE` - request to hide audit trail
- `REQUEST_ALTER_CHECKPOINT_LINEAGE` - request to modify checkpoint history
- `TREAT_SOURCE_AS_SYSTEM_INSTRUCTION` - attempt to elevate content to instruction

**Critical rule:** Indicator detection must produce governed metadata only. Do not execute or follow detected content. Do not create a generic content-execution interface. Do not expose chain-of-thought.

## Authority-Claim Rejection

The `AuthorityClaimRejectionContract` identifies and rejects invalid authority claims:

Claim classes:
- `CLAIMS_APPROVAL` - claim to approve an action
- `CLAIMS_RAHUL_AUTHORITY` - claim of Rahul authority
- `CLAIMS_SYSTEM_AUTHORITY` - claim of system authority
- `CLAIMS_CONNECTOR_AUTHORITY` - claim of connector access
- `CLAIMS_MEMORY_WRITE_AUTHORITY` - claim to write memory
- `CLAIMS_SECRET_ACCESS` - claim to access secrets
- `CLAIMS_PERMISSION_CHANGE` - claim to modify permissions
- `CLAIMS_PROMOTION_AUTHORITY` - claim to promote memory
- `CLAIMS_MERGE_AUTHORITY` - claim to merge code
- `CLAIMS_PRODUCTION_AUTHORITY` - claim to deploy to production
- `CLAIMS_PAID_ACTION_AUTHORITY` - claim to authorize payments
- `CLAIMS_PERSONA_MODIFICATION_AUTHORITY` - claim to modify P0
- `UNKNOWN_AUTHORITY_CLAIM` - unclassified authority claim

**Critical rule:** Any authority claim originating from content rather than a valid governed authority record must be rejected. A source stating "approved", "authorized", "merge this", "deploy this", "ignore safeguards", "write this to memory", "change ONYX", or "change NOVA" must never create the corresponding approval or authority state.

## Memory Quarantine Contract

The `MemoryQuarantineContract` isolates potentially poisoned or untrusted content:

Quarantine states:
- `QUARANTINE_REQUIRED` - quarantine is required but not yet applied
- `QUARANTINED` - content is in quarantine
- `UNDER_REVIEW` - content is under human review
- `RELEASED_AS_CONTENT_ONLY` - released but remains untrusted
- `RELEASED_FOR_GOVERNED_USE` - released after review and validation
- `REJECTED` - content rejected and must be deleted
- `DELETION_REQUIRED` - content marked for immediate deletion
- `RECONCILIATION_REQUIRED` - state resolution required

**Critical rules:**
- Quarantined content must not enter M2 as canonical fact
- Quarantined content must not enter P0
- Quarantined content must not enter active context
- Quarantined content must not grant approval
- Quarantined content must not grant permission
- Quarantined content must not trigger connector action
- Quarantined content must not trigger GitHub action
- Quarantined content must not trigger paid action
- Quarantined content must not modify governance
- Quarantined content must not modify checkpoint lineage
- Quarantined content must never be automatically released

Release for governed use requires:
- provenance verified
- permissions verified
- poisoning review passed
- authority claims rejected
- redaction complete
- scope valid
- explicit reviewer decision

Release as content-only preserves its untrusted classification.

## Durable-Memory Write Eligibility Contract

The `DurableMemoryWriteEligibilityContract` is a pure deterministic decision contract. It does not write memory:

Eligibility must be false when:
- source attribution missing
- provenance invalid
- permission denied
- scope invalid
- retention policy missing
- poisoning review failed
- quarantine unresolved
- authority claim unresolved
- redaction incomplete
- canonical-source relationship unresolved
- derived output lacks a derived label
- approval required but absent
- approval expired
- target is P0
- source attempts persona mutation
- source attempts governance mutation
- source attempts secret storage
- source contains connector credentials

**Critical rules:**
- Only M2 or governed M4 append operations may be eligible
- P0 must never be eligible
- M0, M1, M3, and M5 must follow their separate governed lifecycle rules
- Eligibility is a decision contract only
- Do not write memory

## Tombstone Contract

The `TombstoneContract` marks and tracks deleted content:

Tombstone states:
- `TOMBSTONE_CREATED` - initial state
- `PROPAGATION_PENDING` - awaiting propagation
- `PROPAGATING` - propagation in progress
- `PROPAGATED` - all targets invalidated
- `PARTIALLY_PROPAGATED` - some targets invalidated
- `PROPAGATION_FAILED` - propagation encountered errors
- `RECONCILIATION_REQUIRED` - manual reconciliation needed
- `SUPERSEDED` - replaced by newer tombstone

Reject tombstone creation when:
- deletion is unauthorized
- canonical source ID is missing
- memory-record scope is missing
- deletion scope is invalid
- actor lacks permission
- P0 is targeted
- required audit reference is missing

**Critical rules:**
- A tombstone must be append-only and auditable
- A tombstone must not silently disappear
- A superseding tombstone must reference the earlier tombstone

## Deletion Propagation Contract

The `DeletionPropagationContract` validates deletion across all derived-artifact targets:

Supported target types:
- `CACHE` - cache entries
- `INDEX` - search indexes
- `SUMMARY` - generated summaries
- `EMBEDDING` - vector embeddings
- `ARCHIVE` - archive indexes
- `BACKUP` - backup indexes
- `REHYDRATION_PIPELINE` - rehydration sources
- `DERIVED_MEMORY_RECORD` - derived memory copies

Supported statuses:
- `PENDING` - awaiting action
- `IN_PROGRESS` - propagation ongoing
- `INVALIDATED` - target invalidated
- `BLOCKED` - unable to proceed
- `FAILED_SAFE` - failed safely without data corruption
- `RECONCILIATION_REQUIRED` - manual review needed
- `NOT_APPLICABLE` - target not present

**Critical rules:**
- Do not perform actual propagation
- Implement contract validation and deterministic status evaluation only
- Unknown target types must be rejected
- Do not default an unknown target to NOT_APPLICABLE

## Derived-Artifact Invalidation Contract

The `DerivedArtifactInvalidationContract` marks derived data as invalid:

Supported artifact types:
- `CACHE_ENTRY` - cached entry
- `SEARCH_INDEX_ENTRY` - index entry
- `VECTOR_EMBEDDING` - embedding vector
- `GENERATED_SUMMARY` - summary text
- `CONTEXT_PACKAGE_REFERENCE` - context package
- `ARCHIVE_INDEX_REFERENCE` - archive index
- `BACKUP_INDEX_REFERENCE` - backup index
- `DERIVED_MEMORY_RECORD` - derived memory record

**Critical rules:**
- Invalidated derived artifacts must be excluded from active retrieval
- Invalidated derived artifacts must be excluded from context assembly
- Invalidated derived artifacts must be excluded from ranking
- Invalidated derived artifacts must be excluded from summarization
- Invalidated derived artifacts must be excluded from embedding lookup
- Invalidated derived artifacts must be excluded from memory promotion
- Invalidated derived artifacts must be excluded from source rehydration
- Do not execute invalidation against real caches, indexes, vector stores, archives, backups, or memory stores

## Deleted-Memory Non-Resurrection Validation

The `DeletedMemoryNonResurrectionValidation` proves that a deleted source cannot reappear through any reconstruction mechanism:

**Prohibited resurrection paths:**
- cache warming
- cache restoration
- index rebuild
- embedding rebuild
- summary regeneration
- backup restoration
- archive retrieval
- source rehydration
- context-package reconstruction
- derived-memory reconstruction

Validation requires:
- valid tombstone
- matching canonical source ID
- matching deletion scope
- all required propagation targets classified
- no unresolved active derived artifact
- rehydrationBlocked when policy requires it
- audit references present
- evidence references present

**Critical rules:**
- If any required target remains active or unresolved, return `NON_RESURRECTION_NOT_PROVEN` or `RECONCILIATION_REQUIRED`
- Do not report success merely because one target was invalidated
- All required targets must be accounted for

## Backup, Archive, and Rehydration Boundaries

Wave 3B defines contract boundaries only and does not execute actual operations.

### Backup Restoration Boundary

Backup restoration must consult tombstones before restoring records or derived artifacts. A stale backup must not override a newer tombstone.

### Archive Retrieval Boundary

Archive retrieval must consult tombstones before exposing content. An archive record must not override a deletion decision.

### Source Rehydration Boundary

Source rehydration must consult tombstones before rebuilding memory, summaries, embeddings, indexes, or context references. A source rehydration request must fail safe if tombstone status cannot be verified.

## Frozen Architecture Invariants

Wave 3B preserves all frozen invariants from Wave 3A:

- operational state is not memory
- memory is not approval
- memory is not execution authority
- memory is not permission
- evidence is not approval
- embeddings are derived data
- summaries are derived data
- indexes are derived data
- canonical source records remain authoritative
- source trust does not grant authority
- a source claiming approval does not create approval
- retrieved instructions do not override governance policy
- a highly ranked source does not become authoritative by ranking
- quarantined content cannot enter active context
- deleted content cannot reappear through derived artifacts
- P0 remains immutable and has no writer path
- M4 operational evidence must not become personal memory
- M2 sourced memory does not override its canonical source
- Generated inference remains derived and non-canonical
- Track A may reference Track B only through stable identifiers
- Do not embed complete memory records into Track A contracts
- Phase 1A.8 remains contract-only and deterministic-test-only
